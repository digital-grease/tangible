# Contributing

Tangible is currently in pre-alpha design and scaffold development.

## Before contributing

Read the architecture section of `README.md`, then the crate you intend to
change. The crate-level documentation states what each one is responsible for
and which invariants it holds; the tests are named after the rules they
protect, so a failing test tells you which rule you crossed.

Open an issue before implementing a change that alters the deployment topology, storage model, supported image semantics, security boundary, or public API.

## Development setup

The repository will expose a `Justfile` as the supported developer interface:

```bash
just setup
just dev
just fmt
just lint
just test
just test-integration
just check
```

Real optical-drive tests are never part of the default suite:

```bash
TANGIBLE_HARDWARE_TESTS=1 just test-hardware
```

The hardware suite must also require a configured test drive and explicit test-media policy. Merely setting one environment variable must not be enough to overwrite arbitrary inserted media.

A change to a parser of untrusted input (CUE, TOC, ISO, manifests, paths, burn-tool output) should be fuzzed before review. This needs a nightly toolchain and `cargo-fuzz`; see `fuzz/README.md`:

```bash
just fuzz cue 600
```

An input the fuzzer finds goes into `fuzz/regressions/<target>/` with the fix, so `just test` replays it from then on.

## Pull requests

A pull request should:

- Solve one coherent problem.
- Include tests for behavior changes.
- Update documentation and OpenAPI where applicable.
- Avoid unrelated formatting or dependency churn.
- Describe migration and compatibility effects.
- State which checks were run.
- Identify any hardware validation that remains outstanding.

## Commit style

Use descriptive imperative commits:

```text
Add artifact manifest persistence
Reject CUE paths outside staging root
Implement burn job lease renewal
Document RomM export reconciliation
```

Do not include secrets, private tracker URLs, copyrighted disc-image fixtures, or large binary images in commits.

## Test fixtures

Fixtures must be:

- Generated by the project.
- Public-domain or freely redistributable.
- Minimal enough for source control.
- Accompanied by provenance and generation instructions.
- Free of proprietary software, keys, or personal data.

Large generated fixtures belong in a separately versioned test-fixture release or CI cache.

## Security reports

Do not open a public issue for a suspected vulnerability. Until a private reporting channel is configured, contact the repository owner directly and provide:

- affected version or commit
- reproduction steps
- impact
- suggested mitigation if known

See `SECURITY.md`.

## Design decisions

A change to a foundational decision (deployment topology, the storage model,
artifact identity, the burn-engine strategy, a trust boundary, or public API
compatibility) needs an architecture decision record explaining what changed
and why. Accepted records are not edited to hide history; supersede them with a
new one.

## Licensing of contributions

Tangible is `AGPL-3.0-or-later`. There is no CLA and no DCO sign-off: opening a
pull request offers your contribution under the repository's licence, which is
the ordinary inbound=outbound convention.

One consequence worth stating plainly, because it is a promise rather than an
omission: the project cannot be relicensed without the agreement of every
contributor. Nobody, including the maintainer, can take Tangible proprietary or
grant a closed-source exception unilaterally. That is deliberate: the licence
exists so operators keep control of the software running on their own hardware,
and reserving the power to revoke that would contradict the point.

New files carry:

```
SPDX-FileCopyrightText: <year> <your name or handle>
SPDX-License-Identifier: AGPL-3.0-or-later
```
